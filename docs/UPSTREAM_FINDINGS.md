# Upstream findings

Defects and limitations found by building the L0 asserted corpus
(`core/src/test/resources/stress/`, generated by `scripts/corpus/`). Each is minimized to
the smallest source that reproduces it, and each says plainly whether the fault is in
legend-engine, in legend-lite, or in the corpus itself.

Reproduce any of them with:

```
cd tools/engine-runner && mvn -o compile -q
java -cp target/classes:$(cat cp.txt) perf.TestableMain <files...> [--testable=<fqn>] [--dump=<dir>]
```

Engine version: `4.138.2`.

---

## F1 — legend-engine crashes with a raw ClassCastException on a mixed `~[...]` column array

**Severity: bug (bad diagnostic on an unsupported construct).** Not a wrong answer, but the
failure mode is an internal cast error with no source information, which makes it very
expensive to locate in a large model. The equivalent all-bare array produces a clean,
actionable message.

`ValueSpecificationBuilder.processColSpecArray` decides the array kind by inspecting only
the **first** element, then casts every element to that kind:

```java
String className = resO instanceof ColSpec ? "...ColSpecArray"
                 : resO instanceof AggColSpec ? "...AggColSpecArray"
                 : "...FuncColSpecArray";
```

So `~[a, b:x|$x.b]` is classified `ColSpecArray` from `a`, and the `FuncColSpec` `b` then
fails the cast.

Three variants over an identical model, all from a Class source:

| `project(~[...])` | result |
|---|---|
| `~[firstName, lastName]` | clean: `Can't find a match for function 'project(Person[*],ColSpecArray<...>)'` |
| `~[fn:p\|$p.firstName, ln:p\|$p.lastName]` | compiles and runs |
| `~[firstName, ln:p\|$p.lastName]` | **`ClassCastException: Root_meta_pure_metamodel_relation_FuncColSpec_Impl cannot be cast to ...relation.ColSpec`** |

Stack:

```
ValueSpecificationBuilder.lambda$processColSpecArray$8e20e409$1(ValueSpecificationBuilder.java:481)
ValueSpecificationBuilder.processColSpecArray(ValueSpecificationBuilder.java:481)
ValueSpecificationBuilder.visit(ValueSpecificationBuilder.java:358)
```

**Expected:** the same `Can't find a match for function 'project(...)'` diagnostic the
all-bare case already produces, naming the source location.

Minimized model: `scripts/corpus/repro/mixed-colspec/`.

## F2 — `###Data` Relational CSV cannot express the empty string

**Severity: limitation, arguably a bug.** Both a bare empty field and a quoted `""` are
read back as SQL NULL. There is therefore **no way** to seed an empty-string value through
`###Data`, and any assertion expecting `""` is unsatisfiable.

This matters because empty-vs-NULL is a real and frequently mishandled distinction in
warehouse data — precisely the kind of thing a test corpus exists to pin.

```
###Data
Data demo::EmptyProbe
{
  Relational
  #{
    default.PERSON:
      'ID,FIRST_NAME,LAST_NAME\n' +
      '1,bare-empty,\n' +
      '2,quoted-empty,""\n' +
      '3,nonempty,Smith\n';
  }#
}
```

Query `|demo::Person.all()->project(~[fn:p|$p.firstName, ln:p|$p.lastName])` returns:

```json
[ { "fn" : "bare-empty",   "ln" : null    },
  { "fn" : "quoted-empty", "ln" : null    },
  { "fn" : "nonempty",     "ln" : "Smith" } ]
```

Row 2 should be `""`. Note the CSV parser *does* honour quoting in general — upstream's own
`legend-testable-relational-service-csv-test-data.pure` round-trips `"Doe, Jr"` with an
embedded comma — so this is specifically the empty case collapsing to NULL.

**Consequence for this corpus:** adversarial property A9 (EMPTY_VS_NULL) is withdrawn, and
`seed.check()` now *rejects* any empty-string value so it can never silently degrade to
NULL. See `scripts/corpus/seed.py`.

Minimized model: `scripts/corpus/repro/empty-string/`.

## F3 — legend-lite accepts `BOOLEAN` as a relational column type; legend-engine rejects it

**Severity: parser divergence (legend-lite is wrong).**

Legend's relational grammar has no `BOOLEAN`. `RelationalDataType` accepts
`BIT, INT, INTEGER, BIGINT, SMALLINT, TINYINT, TIMESTAMP, DATE, NUMERIC, DECIMAL, FLOAT,
DOUBLE, REAL, ARRAY, VARCHAR, CHAR, OTHER, SEMISTRUCTURED, JSON` — `BIT` is the boolean.

```
###Relational
Database demo::DB
(
  Table T (ID INTEGER PRIMARY KEY, FLAG BOOLEAN)
)
```

legend-engine: `PARSER error: Unsupported column data type 'BOOLEAN'`
(`RelationalParseTreeWalker.visitColumnDefinition:501`).
legend-lite: accepts it.

Because legend-lite accepted it, the stress corpus shipped **194 columns** across its 200
tables that no other Legend engine could parse. Fixed in this repo by moving to `BIT`.

## F4 — a header-less file is parsed under the preceding section's grammar, and the error names no source

**Severity: divergence, and a corpus trap.**

Sources are concatenated in filename order. `89-all-mapping.pure` opens a `###Mapping`
section; `90-cross-domain-associations.pure` began with a comment and then `Association`
declarations with **no `###Pure` header**. legend-engine therefore parsed 44 associations
with the Mapping grammar and failed with:

```
EngineException: Unexpected token
  at MappingParserGrammar.definition(MappingParserGrammar.java:330)
```

— with **no source information**, so the error names neither the file nor the line. legend-lite
parsed the same bytes without complaint.

Two separate issues worth raising upstream:

1. the `Unexpected token` error carries no `SourceInformation`, which for a 586 KB
   concatenated model means bisecting by hand;
2. legend-lite's section handling is more permissive than the reference parser.

Fixed in this repo by adding the required `###Pure` header.

## F5 — the stress services projected bare column names against a Class source

**Severity: corpus defect, surfaced only because F1 crashed.**

All 12 services were written as
`trading::Trade.all()->project(~[tradeId, tradeDate, instrName:t|$t.instrument.name, ...])`.
A bare `ColSpec` names a column of a **Relation**; a Class has no columns, so the form is
meaningless from `Class.all()`. legend-lite accepted it and generated correct-looking SQL,
which is how it survived.

Regenerated canonically as one `FuncColSpec` per column
(`tradeId:x|$x.tradeId`). Column aliases — and therefore every expectation — are unchanged.

## Non-findings, recorded so they are not re-investigated

- **Row order is not asserted by `EqualToJson`.** The comparator is
  `NULL_MISSING_EQUIVALENT_AND_UNORDERED_ARRAYS`, and two services whose rows came back in
  a different order than the oracle produced them still passed. Confirmed by multiset
  comparison of the dumped payloads. A corpus using this harness therefore **cannot**
  assert ordering, only which rows survive `->sort()->limit()`. `oracle.evaluate` refuses
  any case where a tie straddles the limit boundary, for exactly this reason.
- **Timestamps render as `2024-06-03T19:00:00.000000000+0000`**, dates as `2024-06-03`.
  Not a defect — but undocumented anywhere we could find, and the difference between the
  two is the whole reason 8 of 12 services failed on the first calibrated run.
- **Service testSuites always execute against H2**, whatever the declared connection type;
  `TestRuntimeBuilder` swaps the runtime's connections for a seeded local H2. The stress
  runtime declares DuckDB and the tests still run — so this harness cannot be used for
  dialect-invariance testing.
