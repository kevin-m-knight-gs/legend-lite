## Reproducing the sweep

```bash
cd ~/legend/legend-lite
LEGEND_ENGINE_ROOT=~/legend/legend-engine \
LEGEND_PURE_ROOT=~/legend/legend-pure \
caffeinate -dims tools/allgates.sh
cat ${TMPDIR:-/tmp}/gates-$(id -un).log
```

`caffeinate` is load-bearing — `docs/GATES.md` records a 21× timing error from a
slept run. `tools/allgates.sh` has no `set -e` and always exits 0; read the log.

Single family, with per-test detail (a scoped run never rewrites the scoreboard):

```bash
mvn -o -f pom.xml -pl core test -Dtest=RelationalCorpusRunner \
    -Drcorpus.only=<family-substring> \
    -Dlegend.engine.root=$HOME/legend/legend-engine
```

Add `-Drcorpus.test=<testName>` for one test, `-Drcorpus.backend=h2` for the
second execution target, `-Drcorpus.walls` to dump the 1008 dropped elements,
`LL_TMP_DEBUG=1` for resolver tracing.

**Two traps** (`docs/GATES.md`): `-Dlegend.engine.root` is a *system property*,
not the `LEGEND_ENGINE_ROOT` env var — only `allgates.sh` converts one to the
other, so a hand-run `mvn` silently reads the default checkout. And `mvn -pl core`
resolves `legend-lite-core` from `~/.m2`, not the reactor, so run gate 2 (or
`-am`) after touching core or you A/B the previously installed jar.

## Regenerating the analysis

All scripts honour `BURNDOWN_OUT` (default `/tmp/burndown`) and read the
committed `docs/RELATIONAL_CORPUS.md` plus the live corpus. Run in order:

```bash
export BURNDOWN_OUT=/tmp/burndown
cd docs/burndown-2026-08-14/tools
python3 ledger.py     # scoreboard -> failing.json / failing.tsv   (276 rows)
python3 features.py   # + body-shape flags, assert vocabulary      (276 rows)
python3 master.py     # -> master.csv, the 11-bucket classification
python3 cluster.py    # -> clusters.json, 92 error signatures
python3 dossier.py    # -> dossiers/<family>.md, FULL source of every failing test
```

Independent of the scoreboard:

```bash
python3 recon3.py     # the §1 census defect: 2575 runnable / 2721 total / 77 ToFix-only
python3 census3.py    # the whole-repo <<test.Test>> census -> engine-tests.csv (5390 rows)
python3 famdiff.py    # per-family grep-vs-sweep reconciliation
```

`dossiers/` is the "line by line" artifact — every failing test's complete `.pure`
body next to its untruncated failure detail, grouped by family. ~10.5k lines, so
it is regenerated rather than committed. `engine-tests.csv` is 1.9 MB for the same
reason; `census3.py` rebuilds it in about 20 seconds.

## Key reproductions

**§1 census defect** — `python3 recon3.py` prints `2575 runnable / 2721 total`
against the scoreboard's `2575 / 2798`, and `77` `ToFix`-without-`test.Test`
functions. Root cause: `core/src/test/java/com/legend/rcorpus/Runner.java:443-460`.

**§2.1 SHAPE mislabelling** — 82 of 95 SHAPE rows carry the real cause after an
em-dash:

```bash
python3 -c "
import json,os
f=json.load(open(os.environ['BURNDOWN_OUT']+'/features.json'))
sh=[r for r in f if r['status']=='SHAPE']
print(len(sh),'SHAPE;', len([r for r in sh if ' — ' in r['detail']]),'carry a real cause')"
```

Root cause: `core/src/main/java/com/legend/harness/EngineTestExecutor.java:878-886`.

**§3.1 DuckDB row-order** — the decisive experiment:

```bash
mvn -o -f pom.xml -pl core test -Dtest=RelationalCorpusRunner \
    -Drcorpus.backend=h2 -Drcorpus.only=tests/mapping/selfJoin,tests/mapping/filter,tests/mapping/tree \
    -Dlegend.engine.root=$HOME/legend/legend-engine
```

Expect `tests/mapping/filter: 9/9` (DuckDB gives 8/9) and
`tests/mapping/selfJoin: 2/3` with both `ROOT/TDSNull` tests passing. The control
is `testSelfJoinPropertyMapping`, which uses order-insensitive
`assertSameElements` over the same query and passes on DuckDB already.

**§3.2 invisible comparator failure** — reproduces on both backends:

```bash
mvn -o -f pom.xml -pl core test -Dtest=RelationalCorpusRunner \
    -Drcorpus.only=tests/mapping/tree -Dlegend.engine.root=$HOME/legend/legend-engine
```

Expect `FAIL … testJoinIsolationDeeper_LeftOuterLeftOuterThenInner: assertEquals:
expected [11, OrgName3], got [11, OrgName3]`.
